# ADR-0001: Open-core модель — открытое ядро верификации, платный обновляемый hardening-слой

## Статус

Принято, 2026-10-21.

## Контекст

Изначальный план — продавать `keyforge-shield` как закрытый коммерческий SDK защиты
бинарей (аналог Themida/Sentinel LDK/CodeMeter), поставляемый компилированным
артефактом. Разбор рынка (см. обсуждение) показал:

- У безымянного вендора без репутации и трек-рекорда закрытое security-решение
  никто не купит — покупатель не может аудировать крипто-логику, которой
  предлагается доверить защиту своего продукта.
- Готовых открытых решений, закрывающих весь набор требований (крипто-стойкая
  офлайн-верификация + анти-RE + graceful degradation, кросс-платформенно,
  встраиваемо в любой язык через стабильный ABI), на рынке нет — нишу
  приходится закрывать самим.
- Есть прямой прецедент монетизации именно через раскрытие ядра: Snort (открытый
  IDS-движок, полностью аудируемый) монетизируется через подписку на обновляемые
  правила обнаружения (Sourcefire VRT / Emerging Threats Pro) — ядро открыто,
  платно — актуальность данных, которые устаревают быстрее, чем их можно
  публиковать бесплатно.
- Принцип Керкгоффса: криптографическая часть (формат токена, схема подписи)
  должна оставаться стойкой при полной публичности алгоритма — секретен только
  ключ. Публикация этого слоя не ослабляет защиту, а даёт бесплатный аудит
  сообществом, которого у неизвестного вендора иначе не будет.
- Анти-tamper-техники (тайминг-инварианты, расположение decoy-проверок, схема
  деградации) реальной секретностью обладают лишь временно: даже закрытые
  Denuvo/Themida в итоге обходят реверсеры — закрытость кода не даёт постоянной
  защиты, только откладывает конкретную атаку.

## Решение

Разделяем продукт на два слоя с разными режимами распространения:

1. **`keyforge` (менеджер ключей) — open source целиком.** Выдача, отзыв,
   ротация ключей, формат токена, протокол активации. Без изменений относительно
   исходного плана.

2. **`keyforge-shield` расщепляется на два слоя:**
   - **Core (open source, Apache-2.0).** Референсная реализация протокола
     верификации: разбор и проверка Ed25519-подписанного токена, базовый C ABI
     (`extern "C"`), эталонный Go-SDK на `purego`. Работает полностью
     самостоятельно — пользователь open-core издания получает честную
     криптографическую проверку ключа без анти-tamper-упрочнения.
   - **Hardening-layer (платно, закрыто, распространяется только
     компилированным артефактом).** Анти-RE-механики: разбросанные по коду
     проверки, тайминг-инварианты между вызовами, тихая деградация вместо
     краша при обнаружении подмены. Поставляется как регулярно обновляемая
     нативная библиотека (по модели подписки на правила Snort/ET Pro — клиент
     получает свежий бинарный слой, не исходники). Core-библиотека работает и
     без него; hardening-слой — опциональная надстройка, которую core
     пытается подгрузить и использует, если она присутствует.

Интеграция: core и hardening — отдельные динамические библиотеки с общим C ABI
контрактом. Go-SDK грузит core обязательно, hardening — best-effort
(`purego.Dlopen` с graceful fallback: если библиотеки нет или она не
резолвится, SDK логирует "open-core mode" и продолжает работать без
упрочнения). Так в коде физически видна граница open/paid, а не только в
документации.

## Последствия

**Плюсы:**
- Доверие и дистрибуция через открытость крипто-ядра — снимает проблему
  "купить защиту у вендора с нулевой репутацией".
- Монетизация не требует закрывать то, что и так не даёт постоянной защиты
  (анти-tamper-техники), только то, что действительно теряет ценность при
  публикации немедленно (актуальные, невскрытые техники упрочнения).
- Чёткая архитектурная граница open/paid снижает риск случайно утащить платный
  код в открытый репозиторий — это два разных крейта/модуля с разными
  лицензиями с первого дня.

**Минусы / риски:**
- Hardening-слой без исходников всё равно обходим при достаточной мотивации
  (как и у коммерческих аналогов) — закладываем ротацию техник как постоянный
  процесс, а не разовую задачу.
- Нужен отдельный приватный репозиторий/pipeline для hardening-слоя с иной
  моделью доставки (подписка, версионирование совместимости с core ABI).
- Публикация core — это публикация и формата токена, и протокола активации
  целиком; ревокация/защита от повторного использования токена должна быть
  спроектирована так, чтобы не опираться на секретность самого протокола
  (соответствует принципу Керкгоффса, но требует дисциплины в реализации).

## Рассмотренные альтернативы

- **Полностью закрытый коммерческий SDK с самого начала.** Отклонено — нет
  репутации для продажи закрытого security-продукта, рынок это подтверждает.
- **Полностью открытый продукт без платного слоя.** Отклонено — не даёт пути
  к монетизации, хотя остаётся опцией если hardening-подписка не найдёт спрос.
- **Лицензирование стороннего закрытого протектора (Themida/Sentinel/CodeMeter)
  как основы.** Отклонено — выбор задним числом: смысл найден в собственном
  разборе рынка; закрытый чужой слой убивает саму идею открытого core и
  добавляет vendor lock-in на продукт, который продаём как свой.

## Структура после решения

Два репозитория с первого коммита, не один монорепо с последующим разделением:

```
github.com/sarnas-it/keyforge-shield              — PUBLIC (Apache-2.0)
├── docs/adr/0001-...md
├── core/rust/                                     — C ABI, верификация токена
└── core/go/                                       — эталонный Go-SDK

github.com/sarnas-it/keyforge-shield-hardening     — PRIVATE
└── rust/                                           — анти-tamper слой
                                                       (сейчас: stub-заготовка
                                                        контракта загрузки)
```

Контракт между ними — только runtime (`purego.Dlopen` best-effort из core/go,
проверка ABI-версии через `keyforge_core_abi_version()`), никакой compile-time
зависимости публичного репозитория от приватного.
